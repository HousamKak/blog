In VC6, a `(Real)` cast does not round. Only a store to memory does. Getting that one detail right in a box collision test moved a long replay from desyncing at frame 9,600 to frame 79,400, and it is a fair sample of what this post is about: making an Android phone compute a game of Command & Conquer: Generals Zero Hour exactly, to the bit, the way a 2003 compiler did.

Zero Hour came out in 2003. In 2025 EA released its source code under the GPL, and the community did remarkable things with it. One of them is an Android port by [MYSOREZ](https://github.com/MYSOREZ/GeneralsZH-Android-Port) that runs the real engine on a phone, with touch controls and cross-play against the community's GeneralsOnline PC client. I did not write that port. On 8 October 2026 I imported it at v1.4.0 and started maintaining a fork, and between 11 and 14 October I did the work below on top of it. The long chain of people who made any of this possible is credited at the end.

## Retail checks only the simulation

The port was built to play against GeneralsOnline, which runs the community's modernized rules at 60 Hz. I wanted something else: a phone on a LAN against a PC running the original retail Zero Hour 1.04, unpatched.

Generals is a lockstep RTS. Every machine runs the whole simulation and only player orders cross the network. Every frame, each machine hashes its game state into a checksum, and if two machines disagree, the match is out of sync.

I read EA's original source to see what a retail LAN join actually checks. Almost nothing: the INI and executable checksum comparison in `LANAPI::handleRequestJoin` is commented out in retail 1.04, TheSuperHackers keep it off for Zero Hour, and the duplicate serial check passes because the phone sends an empty serial. So it does not matter which store a PC copy came from.

What does matter is the per-frame logic checksum. The phone has to compute the same game, to the bit, as a PC running a binary compiled in 2003.

The port ships two engines: a 60 Hz one for GeneralsOnline cross-play, and a 30 Hz one. I put everything retail-specific behind one build switch, `SAGE_RETAIL_RULES`, compiled only into the 30 Hz engine. Nothing in this post touches the 60 Hz engine.

## A modern compiler is not a reference

Retail Zero Hour was compiled with Visual C++ 6, and its floating point runs on the x87 FPU at 24-bit precision. A modern MSVC build of the same source is not retail compatible. Neither is clang on an ARM phone.

So the first job was a reference I could trust. TheSuperHackers' CI checks retail replays with VC6 builds only, so I built their tree exactly the way their CI does: a portable VC6 toolchain from [itsmattkc/MSVC600](https://github.com/itsmattkc/MSVC600) at the pinned commit and hash, their `vc6` preset, run headless against a replay in a retail game folder. One trap: that folder must not contain the GeneralsOnline data patch, because the game's recursive archive scan would quietly mount it.

That reference reproduces the recorded checksums of [TheSuperHackers' retail replay set](https://github.com/TheSuperHackers/GeneralsReplays): nine replays across nine maps, all three factions and Hard AI, 4 to 55 minutes each, about 375,000 frames in total.

Then I added a probe to the reference that writes exactly what the phone's network trace writes at each checkpoint: the checksum parts, the per-object checksums, the matrix words, and at one chosen frame the entire stream of words that goes into the checksum, with section marks. From then on a mismatch was a diff, not a hunt.

## The loop

Every divergence went through the same steps:

1. Replay on the phone at 30 Hz. At the first mismatch, the phone dumps its whole checksum word stream.
2. Dump the reference at the same frame and diff section by section. Every single case was inside the objects section, in one or a few objects.
3. Diff the object's words. Which word, and by how much? A difference of `0x80` in a high byte is a sign bit on a zero. A difference of 1 in the last place is rounding.
4. Read retail's machine code for that function, with `dumpbin /DISASM` on the reference's object file. It says exactly what VC6 computed, in what order, and what it kept in a register.
5. If the value comes from a library function, measure the function: a VC6 harness linked against the reference's own object file, run over millions of inputs, then an exact emulation fitted and checked against all of them.
6. Fix under `SAGE_RETAIL_RULES`, rebuild, rerun every replay.

On 12 October, none of the nine replays reproduced to the end. On 14 October, all nine did.

## What VC6 did that clang does not

Roughly in the order they bit:

**Signed zeros.** VC6 constant-folded `0*a` to `+0` and `0-a` to `-a` inside inlined cross products. IEEE arithmetic gives `-0` in some of those places. The values are equal, the bits are not, and the checksum hashes bits.

**Transcendentals that are never rounded.** Retail's `Sin` compiles to `fld; fsin; ret`. The result sits in an 80-bit x87 register and the caller multiplies it before it is ever rounded to a float. I wrapped these in a small `X87Real` type that rounds once per operation, the way 24-bit x87 does. Checked on 686 infantry moves: all reproduced.

**acos and asin, measured.** Retail's `acos` is computed as `atan2(sqrtf((1-x)(1+x)), x)`. I did not guess that: I fitted it against the reference over 5.36 million inputs and it matched on every one. Along the way I confirmed that `sin`, `cos`, `tan`, `atan`, `atan2`, `sqrt`, `log` and `fmod` match a plain double computation rounded to float exactly.

**Additions in VC6's order.** Floating point addition is not associative, and VC6 regrouped sums per call site. The common one is a vector length computed as `(z*z + y*y) + x*x`, not in source order. Worse, every inlined copy of a helper like `length` or `normalize` gets its own grouping, while the out-of-line copy sums in source order. There were 73 such sites for lengths and dot products alone. The rule I ended up with: never guess, read the listing for the site, then check the order offline against the reference's values.

**Division by a constant.** VC6 at `/O2` divides by a constant by multiplying with its rounded reciprocal, so an INI value of `"120%"` becomes 1.19999993. Clang does the same with `-freciprocal-math`, but goes further: it merges three or more divisions by one variable and hoists loop-invariant divisors, which VC6 never did. Those sites keep real divisions, found by diffing reciprocal divisions per function in the disassembly. That fix alone moved five replays 100 to 2,100 frames further.

**Double promotion.** A double literal in an expression keeps the phone's whole expression in double, with one rounding at the end. Retail rounds every step to 24 bits. The missile lead distance was the big one: a missile's thrust direction was right, but its goal was one unit in the last place off, from a lead distance computed in another file. Fixing it moved four replays 3,000 to 16,000 frames further.

**Values kept in a register.** This is the cast that does not round, from the top of this post. Box corner collision tests store the cosine and keep the sine in a register. Every site like that had to be read, and the box test alone was worth about 70,000 frames of agreement in a single change.

**NaN comparisons.** A compare with a NaN on x87 sets three condition flags at once. Whether VC6's `test ah, MASK` then takes the branch depends on the operand order and the mask, and often differs from IEEE's "always false". A braking factor of 0/0 in the locomotor force cap hit this, and fourteen more compares were NaN sensitive. The fix is to write the logically equivalent form that gives retail's outcome: `a > b` that branches on NaN becomes `!(b >= a)`.

**The x87 exponent.** An x87 register holds a 24-bit mantissa but a much wider exponent, so a product of two tiny matrix entries stays nonzero, and keeps its sign, until it is stored. Rotations now multiply through a register type that models exactly that, and decaying pitch, roll and yaw rates that fall into the denormal range round twice, as x87 does.

**And a few that were not floating point at all.**

- An uninitialized variable in the AI's production code that VC6 happened to leave `true`. With `false`, the AI chose its next building the frame its dozer appeared, one frame before retail. TheSuperHackers already keep it `true` under `#if _MSC_VER < 1300`, so grepping the reference for that condition is a good way to find retail behavior in simulation code.
- The partition solver sorts with `std::sort` from STLport 4.5.3, which is unstable above 16 elements. The phone now uses that exact algorithm.
- A frame count divided as integers in retail had become a float division in the port's 60 Hz work. The only such site in the simulation.
- `BitFlags` hashed `sizeof(this)` bytes of a mask into the checksum: 4 on every PC client, 8 on a 64-bit phone. Invisible until a player activated a battle plan, which put a mask into the checksum.

Two things I suspected and ruled out by measurement: VC6's `sscanf("%f")` is correctly rounded on all 2,081 numbers in the retail INI files, and the per-store executable checksum is never checked on LAN.

## Traps worth knowing

**A trace changes the code it traces.** Adding a log line inside a VC6 function changes how VC6 compiles that function, and the reference stops being retail. Trace from another translation unit, or from the caller.

**When the arithmetic matches, the input does not.** If a function's own operations match the listing and the output still differs, perturb each input by a few ulps offline until the retail output appears, then trace where that input came from.

**One frame early is a decision, not arithmetic.** When a unit stops or the AI acts one frame early or late, log the decision's inputs on both sides, not the math.

**Audit before you chase.** An audit of the simulation against TheSuperHackers' tree, looking for changes that only made sense for the GeneralsOnline rules, found most of them in one pass. If I did this again, I would do that audit on day one and save days of chasing divergences one at a time.

## Where it stands

On 14 October the phone's 30 Hz engine reproduced all nine retail Zero Hour 1.04 replays to their last checkpoint, bit for bit, with the 60 Hz GeneralsOnline engine unchanged.

Not done yet: a live LAN game against a retail PC, and more retail replays for wider coverage. Nine replays reproducing is strong evidence, not proof. A live match exercises the network code too, and I will write that up when it has happened.

(The same week I also added in-app updates, release notes in English and Arabic, and crash reporting through App Monitor, my own telemetry platform, which promptly caught a Galaxy A55 crash inside the GL driver. That one is a story of its own.)

The thing that stays with me is how much of a 2003 compiler's personality lives in a game's behavior. The game's rules are the source code plus every decision VC6 made about it: the order it added things, what it kept in a register, when it rounded. Reproducing the game meant reproducing the compiler, one site at a time.
