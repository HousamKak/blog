Somewhere in the last year I stopped thinking of a user interface as the front door of my software. It is one of the doors. The others are a command line and an MCP server, and an agent uses those every day.

Look across what I have built recently and the same shape keeps appearing:

- **H**, my canvas of terminals and live applets, ships an MCP server (`h-orchestrator`) with about a hundred tools.
- **BlockForge**, the world compiler, has a CLI (`kc.js`) and an MCP server with a couple of hundred tools: build plans, cameras, films, materials, critics, exports.
- **Partforge**, my mechanical part toolset, drives OpenSCAD, Bambu Studio and SolidWorks from one core, through a CLI (`pf`) or 54 MCP tools.
- **Electrical Lab** builds a circuit once and runs it on five backends, through 33 MCP tools.
- **H Distribution**, my self-hosted publishing system, has a CLI where every command returns JSON and an MCP server with about a hundred tools.
- **UIpen** sends what I point at in a browser straight into a Claude Code session.

App Monitor, Budgetability and Comms Hub do it too. It was not a plan. It is a rule I keep arriving at, so I want to write down why, and where it breaks. The projects themselves are on [my work page](https://www.housamkak.com/work).

## The rule

> Anything I can do in the interface, an agent can do through a CLI or MCP, against the same core.

The last four words carry the weight. H Distribution's MCP tools file opens with a comment that says it better than I can:

> Every tool is a thin wrapper over a service-layer function, same contract that the CLI and `/api/v1/*` adapters use.

One core. Three adapters: the UI, the CLI, the MCP server. None of them owns any logic.

## What it buys

### 1. The agent stops guessing

Before UIpen, my feedback loop on UI work was a screenshot and a sentence: "this button is misaligned". The agent then guessed which component that was from pixels. UIpen is a dev-mode overlay where I drop a pin, a region or an arrow on the running app, and the annotation arrives in the session with the DOM selector, the source file, the line and the React component name attached. The agent edits the right file the first time, hot reload refreshes the page, and the pin resolves.

The general version of that lesson: give the agent the same handle on the thing that you have, not a picture of it.

### 2. Agents can see what they did

Acting is half of it. An agent that builds a world and cannot look at it is building blind. BlockForge grew an observation protocol for exactly this: `snapshot` renders the world from any pose off-screen, without moving my camera, and `query` reads blocks back, finds what the camera is looking at, and reports what a build changed. Both clients, native C++ and web, implement the same protocol, so the same tools work whichever one is running.

The Escher Waterfall work leaned on this constantly: render a still, compare it to the reference, measure, change one thing, render again. The loop only works because "look" is a tool call.

### 3. One circuit, many truths

Electrical Lab is the clearest case of the rule paying off. The agent describes a circuit once, in a backend-neutral model of parts, nets and firmware, and then asks the right backend the right question:

| Question | Backend |
| --- | --- |
| Does my firmware logic work? | avr8js, headless, fast |
| What does it look like, and does the mixed circuit behave? | PCBX in a browser workbench |
| Exact voltages, currents, transients | ngspice |
| Schematic, PCB, BOM | KiCad export |
| Share or run it elsewhere | Wokwi export |

Without a model the agent can drive, each of those is a separate tool with its own file format and its own UI. With it, switching backends is one argument.

### 4. Real work gets automated, including the boring bug

Partforge's loop is `pf scad set`, then `pf build`, which renders, measures wall thickness and overhangs, judges printability and slices to real grams and minutes in one pass. Making that headless forced me to find a crash nobody documents: `bambu-studio.exe --slice` with a stock profile dies with an access violation, because the shipped profiles are thin children that `inherits` a parent the CLI never resolves. Partforge walks the chain to the root and deep-merges a flat profile. I would never have hit that clicking through the GUI, and every agent that slices through Partforge now gets it for free.

### 5. Self-discovery

H Distribution has a `schema --json` command that returns every command, subcommand, flag and return shape in one machine-readable catalogue. An agent calls it once and knows the whole surface. Every response has the same shape, `{ ok, message?, error?, data? }`, so there is never any parsing of human prose.

### 6. Software that is wired, not just called

H takes the idea one step further. On the canvas, I drag a wire from a terminal's "Agent link" output to an applet's input, and the agent in that terminal can now drive that applet. It calls `h_my_links` to find what it is wired to, reads the applet's state, and patches it; the tile re-renders live on my screen and the wire pulses. For code rather than data, it reads the applet's HTML, edits it and writes it back with a change note, and the tile hot-reloads with the old version restorable.

My own to-do list is one of those applets. When a session I am running hits something only I can do, it adds an item. That is a strange and pleasant feeling the first time.

## What it costs, and where it fails

The rule is not free, and I have paid for every one of these.

### Two engines drift

H's canvas once had a chat applet that "mirrored" the docked chat's handlers, minus some plumbing. Within weeks they had drifted: the canvas version had no handlers for half the events, so pointing it at certain agents ran them and nothing appeared on the canvas. The fix was to stop having two engines. The canvas agent is now the docked chat, mounted as a node.

That is the same rule from the other side. If the agent surface is a second implementation instead of an adapter over the same core, it will drift, and the agent will be the one who finds out.

### Power needs a person

Some actions should not be one tool call away. Partforge deliberately has **no "start print" MCP tool**. Committing a machine to an hours-long physical job belongs to a person, so it lives in the CLI, where it takes intent. Cloud tools are read-only; LAN tools that move the printer are separately named.

H's vault follows the same principle for secrets. There is no `get_secret` and no plaintext secret argument anywhere in H's MCP. An app declares which key it needs, I bind a vault record to it with explicit approval, and H injects the credential into that app's private process. The model sees the result of the action, never the credential. The docs are honest about the limit, too: this protects the MCP channel, but a coding agent with full shell access can still read files as my user. Real isolation needs a separate OS identity.

So the rule has an amendment: make everything drivable, except the things that should need a human, and make those visibly different.

### Agent surfaces are processes

Every MCP server is a process. Each Claude Code session spawns its own full fleet. One day H's services kept "dying", and they were not buggy: four sessions had spawned about 33 Node processes between them, the laptop sat at 100 percent CPU, health probes timed out, and the watchdog made it worse. Making everything drivable multiplied by everything running at once is a real resource bill. I measured it and fixed it, and [that story gets its own post](/posts/four-claude-sessions-one-laptop/).

### Too many tools is its own interface problem

A couple of hundred tools is a lot to choose from. More tools do not make a better agent; better-named tools with schemas and examples do. BlockForge leans on `tool_info` for field descriptions, H on a live `h_capabilities` summary built from the actual registries, H Distribution on `schema`. The surface needs a table of contents, or the agent guesses.

### Silence is not completion

When agents drive things for you, you need to know when they are done. A terminal going quiet does not mean the agent finished; it might be waiting, stuck, or asking a question no one saw. H derives "done" and "needs attention" from the transcript instead of from silence. Any system built on this rule eventually needs that.

## Why I keep doing it

The honest reason is leverage. I run many projects in parallel, and the agents running them are only as useful as the handles I give them. A UI-only tool is a tool I have to operate myself. A tool with a CLI and an MCP server is one I can hand to a session and check on later.

There is also a design benefit I did not expect. Writing the agent surface first forces the core to be clean: if a feature cannot be expressed as a function with typed inputs and a structured result, it is usually tangled with its UI, and that is a smell for humans too.

So the rule, as I now state it:

1. One core. The UI, the CLI and the MCP server are adapters over it, never reimplementations.
2. Structured in, structured out. JSON results, schemas, a self-describing catalogue.
3. Let the agent see, not just act.
4. Physical, financial and secret actions need a person, and look different.
5. Count the processes.

If you want to see these tools individually, they are on [housamkak.com/work](https://www.housamkak.com/work). Every one of them can be driven by an agent. Almost every one of them was built with one, too.
